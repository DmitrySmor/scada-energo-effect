# Техническое задание: SCADA Backend

## 1. Назначение проекта

Разработать SCADA Backend для приёма, проверки, хранения и предоставления данных от приборов учёта и датчиков различных типов: газовых и электрических счётчиков, датчиков температуры, давления и другого оборудования.

Frontend в рамках проекта не разрабатывается.

Backend не рассчитывает расход и не вычисляет новые измерительные показатели. Его задачи — принимать исходные данные, проверять их, сохранять и предоставлять через API.

## 2. Технологический стек и окружение

- ОС: Debian 13.
- Развёртывание: Docker Compose.
- Backend: Python, FastAPI, Pydantic.
- База данных: PostgreSQL с обязательным TimescaleDB с первого развёртывания.
- Передача сообщений: MQTT.
- Формат сообщений: JSON.
- API-документация: OpenAPI и Swagger UI, автоматически формируемые FastAPI.
- Каталог проекта: `/opt/docker/iot-project/`.

## 3. Docker и хранение данных

- Все необходимые сервисы подключаются к существующей Docker network `proxy`.
- В Docker Compose сеть `proxy` указывается как внешняя (`external: true`). Проект не должен создавать или удалять эту сеть.
- Дополнительные Docker-сети разрешены для изоляции сервисов.
- Именованные Docker volumes не использовать для постоянных данных.
- Постоянные данные хранить через bind mounts с хоста в каталогах `/data/<container_name>/`.
- Данные должны сохраняться при пересоздании контейнеров.
- Настроить необходимые права доступа к каталогам с учётом UID/GID процессов внутри контейнеров.
- Резервные копии хранить отдельно от основного диска с данными.

## 4. MQTT: подключение и безопасность

MQTT-брокер доступен из интернета, но подключаться к нему и публиковать сообщения могут только зарегистрированные устройства.

Обязательные требования:

- Все внешние MQTT-соединения защищены TLS.
- Анонимный доступ запрещён.
- Каждое устройство имеет индивидуальные учётные данные.
- Для каждого устройства настраиваются индивидуальные ACL.
- Устройство может публиковать сообщения только в разрешённые ему топики.
- Публикация в топики других устройств запрещена.
- Подписка устройств на топики запрещена, если отдельно не согласована.
- Незашифрованный MQTT-порт не должен быть доступен извне.
- Учётные данные устройств можно отзывать и заменять.
- Неудачные подключения и нарушения ACL логируются.

Backend должен дополнительно проверять регистрацию устройства, соответствие устройства объекту учёта и право публикации в указанный топик.

## 5. MQTT: QoS и надёжность доставки

- Для публикации телеметрии, статусов, диагностики и событий устройства используют **QoS 1 (At Least Once)**.
- MQTT-брокер и backend должны поддерживать приём сообщений с QoS 1.
- QoS 1 предусматривает доставку как минимум один раз, поэтому одно логическое сообщение может быть доставлено повторно.
- Каждое логическое сообщение должно иметь уникальный `message_id`. При повторной отправке или доставке того же сообщения идентификатор сохраняется.
- Backend должен обеспечивать идемпотентную обработку и исключать повторное создание показаний, событий и других записей для одного логического сообщения.
- Брокер должен отправлять MQTT-подтверждение `PUBACK` в соответствии с протоколом QoS 1.
- Получение `PUBACK` **не означает, что сообщение успешно обработано backend или сохранено в базе данных**.

### 5.1. Прикладное подтверждение сохранения

Необходимо реализовать отдельный механизм прикладного подтверждения, позволяющий устройству узнать, что сообщение успешно обработано backend и сохранено в PostgreSQL/TimescaleDB.

Требования:

- Прикладное подтверждение отправляется только после успешной валидации, обработки и фиксации необходимых данных в базе данных.
- Подтверждение должно содержать как минимум `message_id` и результат обработки.
- Успешный результат означает, что данные надёжно записаны в базу данных и транзакция успешно завершена.
- Для неуспешной обработки предусмотреть отдельный результат с кодом и описанием ошибки, если сообщение удалось принять и идентифицировать.
- Прикладные подтверждения публикуются в отдельный MQTT-топик или топики, доступные только соответствующему устройству согласно ACL.
- Формат подтверждения, названия топиков и перечень кодов результата документируются в спецификации MQTT.
- Backend не должен подтверждать успешное сохранение до завершения транзакции записи.
- Повторная обработка уже сохранённого сообщения должна возвращать согласованный результат, не создавая дубликатов.
- При потере соединения до получения прикладного подтверждения устройство должно иметь возможность повторить отправку того же сообщения с тем же `message_id`.
- Повторная отправка не должна приводить к повторному созданию данных.

При необходимости устройство должно хранить неподтверждённые сообщения локально и повторять отправку после восстановления связи. Конкретная реализация очереди на стороне устройства определяется отдельно.

### 5.2. MQTT-сессии

Параметры MQTT-сессий должны учитывать временные отключения устройств и необходимость повторной доставки сообщений. Для выбранной версии MQTT необходимо определить и документировать параметры сохранения сессии и очереди сообщений, включая соответствующие настройки MQTT 5 или MQTT 3.1.1.

## 6. MQTT-топики

Используется универсальная структура топиков:

`scada/v1/{object_id}/{device_id}/{message_type}`

Допустимые типы сообщений:

- `telemetry` — измерения;
- `status` — состояние устройства;
- `diagnostics` — диагностическая информация;
- `event` — события.

Структура не должна быть привязана исключительно к газовому оборудованию. Тип устройства, модель, параметры и единицы измерения определяются конфигурацией и описанием модели.

При обработке проверяются регистрация устройства, его принадлежность к объекту из топика и право публикации в соответствующий топик.

Для прикладных подтверждений необходимо предусмотреть отдельную структуру топиков с индивидуальными правами доступа. Устройство должно иметь возможность получать только собственные подтверждения. Формат и точные имена топиков фиксируются при реализации.

## 7. Формат MQTT-сообщений

Сообщения передаются в формате JSON.

Пример:

```json
{
  "schema_version": "1.0",
  "message_id": "unique-message-id",
  "device_id": "device-001",
  "measured_at": "2026-01-01T12:00:00Z",
  "sequence": 123,
  "message_type": "telemetry",
  "data": {}
}
```

Обязательные поля:

- `schema_version`;
- `message_id`;
- `device_id`;
- `message_type`;
- `data`.

Необязательные поля:

- `measured_at`;
- `sequence`.

Требования:

- `message_id` уникален для каждого логического сообщения и не меняется при повторной отправке.
- `data` валидируется по схеме соответствующего типа устройства и сообщения.
- Схема описывает параметры, типы данных и единицы измерения.
- Добавление нового типа оборудования не должно требовать изменения общей логики приёма MQTT-сообщений.
- Время получения `received_at` назначается сервером в UTC.
- Исходный JSON сохраняется для аудита и диагностики, в том числе при ошибках обработки, если сообщение удалось принять.

### 7.1. Формат прикладного подтверждения

Пример успешного подтверждения:

```json
{
  "schema_version": "1.0",
  "message_id": "unique-message-id",
  "device_id": "device-001",
  "status": "stored",
  "processed_at": "2026-01-01T12:00:01Z"
}
```

Пример неуспешной обработки:

```json
{
  "schema_version": "1.0",
  "message_id": "unique-message-id",
  "device_id": "device-001",
  "status": "rejected",
  "error_code": "VALIDATION_ERROR",
  "error_message": "Message data does not match the configured schema",
  "processed_at": "2026-01-01T12:00:01Z"
}
```

Допустимые значения статуса и их семантика должны быть документированы. `stored` означает, что предусмотренная обработка завершена и данные успешно сохранены. `rejected` означает, что сообщение не принято к сохранению как корректные данные. Получение сообщения MQTT-брокером само по себе не является прикладным подтверждением.

## 8. Обработка сообщений и данные

Backend должен:

- Проверять корректность JSON и обязательных полей.
- Проверять регистрацию устройства и разрешённость топика.
- Проверять соответствие устройства объекту учёта.
- Валидировать данные по настроенной схеме оборудования.
- Сохранять исходное сообщение и статус обработки.
- Сохранять причины ошибок валидации и обработки.
- Обеспечивать дедупликацию по `message_id` и установленным правилам.
- Выявлять нарушения последовательности `sequence`, если поле передано.
- Обрабатывать поздно поступившие сообщения, не позволяя старым показаниям перезаписывать более новые текущие значения.
- Раздельно хранить время измерения и время приёма.
- Не изменять исходные измерения и не рассчитывать новые показатели.
- Отправлять прикладное подтверждение успешного сохранения только после фиксации данных в базе.
- Предусмотреть повторную обработку уже известного `message_id` без дублирования записей.

Ошибочные сообщения, принятые на уровне MQTT и доступные backend, должны сохраняться в `raw_messages` вместе с причиной отказа. Если сообщение не удаётся принять или идентифицировать на транспортном уровне, это отражается в системных логах.

## 9. PostgreSQL и TimescaleDB

TimescaleDB обязательна с первого развёртывания.

Требования:

- Использовать PostgreSQL с установленным и настроенным расширением TimescaleDB.
- Таблицу `readings` реализовать как TimescaleDB hypertable с временным измерением `measured_at`.
- Данные измерений хранить в PostgreSQL/TimescaleDB.
- Предусмотреть эффективные запросы по устройству, параметру и диапазону времени.
- Настроить индексы с учётом сценариев записи и чтения.
- Таблицы компаний, пользователей, устройств, состояний, событий, настроек и исходных сообщений хранить как обычные таблицы PostgreSQL, если для конкретной таблицы не определено иное.
- Настроить транзакционную запись данных и корректную обработку ошибок.
- Прикладное подтверждение `stored` публиковать только после успешного завершения транзакции записи.
- Резервное копирование и восстановление должны учитывать PostgreSQL и TimescaleDB.

## 10. Компании, пользователи и роли

В первой версии предусмотрены только две роли.

### `admin`

Суперпользователь с полным доступом ко всем компаниям, объектам, устройствам, показаниям, событиям и настройкам.

### `user`

Аккаунт компании-клиента, то есть юридического лица, а не отдельного сотрудника.

- В первой версии у каждой компании один аккаунт `user`.
- Отдельные аккаунты сотрудников не реализуются.
- Каждая учётная запись `user` относится ровно к одной компании.
- У компании может быть много узлов учёта.
- Каждый объект учёта принадлежит одной компании через `company_id`.
- Каждый прибор или датчик привязан к одному объекту.
- Компания получает доступ только к собственным объектам и связанным с ними данным.
- Проверка прав выполняется на сервере при каждом защищённом запросе.
- Подмена идентификатора объекта или устройства не должна предоставлять доступ к чужим данным.
- Регистрация компаний, объектов и устройств в первой версии выполняется администратором.
- Компания устройства определяется по регистрации в БД, а не по данным из MQTT payload.

## 11. Основные таблицы

- `companies` — компании.
- `users` — учётные записи и роли.
- `objects` — узлы учёта.
- `devices` — приборы и датчики.
- `readings` — показания, TimescaleDB hypertable.
- `device_state` — текущее состояние устройства.
- `device_events` — события устройств.
- `raw_messages` — исходные сообщения, статусы и причины ошибок.
- `notifications` — уведомления.

Схема должна обеспечивать связи устройств с объектами и компаниями, уникальность идентификаторов сообщений в рамках согласованной модели хранения и контроль доступа.

## 12. REST API

API реализуется на FastAPI с префиксом `/api/v1/`.

- OpenAPI и Swagger UI генерируются автоматически.
- Используются Pydantic-схемы, dependency injection, middleware и стандартные механизмы обработки ошибок FastAPI.
- Аутентификация и авторизация реализуются явно с использованием совместимых механизмов FastAPI.
- Все бизнес-эндпоинты требуют аутентификации.
- Эндпоинты проверки здоровья могут быть доступны без аутентификации.
- История показаний поддерживает фильтрацию по времени, параметру и качеству данных, а также пагинацию.
- API возвращает сохранённые данные и не рассчитывает новые измерительные показатели.
- Все эндпоинты, схемы, коды ошибок и правила доступа документируются в OpenAPI.

### Эндпоинты

| Метод            | Путь                            | Назначение                            |
| ---------------- | ------------------------------- | ------------------------------------- |
| POST             | `/api/v1/auth/login`            | Аутентификация                        |
| GET              | `/api/v1/me`                    | Текущий пользователь, компания и роль |
| GET, POST        | `/api/v1/objects`               | Список и создание объектов            |
| GET, PATCH       | `/api/v1/objects/{id}`          | Получение и изменение объекта         |
| GET              | `/api/v1/objects/{id}/devices`  | Приборы объекта                       |
| POST             | `/api/v1/devices`               | Регистрация устройства                |
| GET, PATCH       | `/api/v1/devices/{id}`          | Получение и изменение устройства      |
| GET              | `/api/v1/devices/{id}/readings` | История показаний                     |
| GET              | `/api/v1/devices/{id}/state`    | Текущее состояние                     |
| GET              | `/api/v1/devices/{id}/events`   | События устройства                    |
| GET, POST, PATCH | `/api/v1/admin/users`           | Управление пользователями             |
| GET              | `/api/v1/health/live`           | Проверка работоспособности процесса   |
| GET              | `/api/v1/health/ready`          | Проверка готовности сервисов          |

Административные эндпоинты доступны только роли `admin`. Роль `user` получает доступ только к данным собственной компании.

## 13. Качество данных

Для показаний предусмотреть статусы качества:

- `valid` — корректные данные;
- `invalid` — данные не прошли обязательную проверку;
- `suspect` — данные приняты, но имеют признаки возможной некорректности;
- `unknown` — качество не определено.

Правила присвоения статусов документируются. Исходные данные сохраняются без изменения.

## 14. Мониторинг устройств и уведомления

Backend должен отслеживать:

- Время последнего сообщения устройства.
- Превышение настраиваемого периода отсутствия данных.
- Потерю связи и её восстановление.
- Ошибки обработки сообщений.
- Повторяющиеся сообщения и нарушения последовательности.

Пороговые значения должны настраиваться.

Уведомления:

- Создавать уведомления для важных событий, включая длительное отсутствие связи и ошибки.
- Подавлять или объединять повторяющиеся одинаковые уведомления.
- Хранить историю уведомлений.
- Обеспечивать видимость уведомлений только соответствующей компании, кроме доступа администратора.
- Предусмотреть расширение каналов доставки и правил повторных попыток.

Полноценный процесс подтверждения и закрытия инцидентов в первую версию не входит.

## 15. Безопасность REST API

- REST API работает по HTTPS.
- API доступен из локальной сети или VPN, кроме явно согласованных публичных маршрутов.
- Пароли хранятся только в виде безопасных хешей.
- Секреты и пароли не размещаются в Git.
- Конфигурационные секреты передаются через переменные окружения или файлы секретов с ограниченными правами.
- Настроить ограничение частоты запросов.
- Проверять входные данные и права доступа на сервере.
- Не записывать пароли, токены и другие секреты в логи.
- Логировать административные действия, ошибки и события безопасности.

- Автоматическая первоначальная настройка расширения TimescaleDB и создание hypertables.
- Пример файла окружения без секретов.
- Инструкции по установке, обновлению, резервному копированию и восстановлению.
- Документация REST API.
- Спецификация MQTT: топики, JSON-схемы, QoS, ACL, прикладные подтверждения и коды ошибок.
- Инструкция по регистрации устройств и подключению к MQTT.

Перенос исторических данных из старой SCADA в проект не входит.

## 20. Критерии приёмки

1. Проект разворачивается на Debian 13 через Docker Compose.
2. Все необходимые сервисы подключены к существующей сети `proxy`.
3. Постоянные данные хранятся через bind mounts в `/data/`.
4. PostgreSQL и TimescaleDB установлены и настроены с первого развёртывания.
5. Таблица показаний создана как TimescaleDB hypertable.
6. Backend умеет записывать и читать показания через TimescaleDB.
7. MQTT-доступ разрешён только зарегистрированным устройствам с индивидуальными учётными данными.
8. Устройство не может публиковать сообщения в чужие топики.
9. Поддерживаются разные типы оборудования через настраиваемые схемы данных.
10. Корректные сообщения сохраняются и доступны через API.
11. Ошибочные сообщения, принятые на уровне приложения, сохраняются с причинами ошибок.
12. Повторная доставка одного `message_id` не создаёт дубликатов.
13. Поздние показания не перезаписывают более новые текущие значения.
14. Сообщения телеметрии и других предусмотренных типов принимаются с QoS 1.
15. MQTT `PUBACK` не считается подтверждением успешного сохранения данных в БД.
16. Прикладное подтверждение `stored` отправляется только после успешной фиксации данных в базе.
17. Прикладное подтверждение содержит идентификатор сообщения и результат обработки.
18. Повторная отправка сообщения с тем же `message_id` не создаёт повторных записей и позволяет получить согласованный результат обработки.
19. При потере связи и повторном подключении корректно обрабатываются повторные доставки.
20. Пользователь компании имеет доступ только к собственным объектам и данным.
21. Попытки доступа к чужим данным через подмену ID блокируются.
22. Администратор имеет полный доступ.
23. OpenAPI и Swagger UI доступны и документируют API.
24. Проверки работоспособности и готовности сервисов работают.
25. Резервное копирование и восстановление проверены.

## 21. Вопросы, требующие согласования

- Количество устройств и частота передачи сообщений.
- Схемы `data` для типов оборудования.
- Механизм REST-аутентификации: JWT или сессии.
- Точные топики и формат прикладных MQTT-подтверждений, коды ошибок и правила повторной отправки.
- Версия MQTT и параметры сессий.
- Каналы доставки уведомлений.
- Место хранения резервных копий вне основного диска.
- Пороговые значения отсутствия данных.
- Сроки хранения показаний, исходных сообщений и логов.
- Ограничения частоты запросов API.
- Требования RPO/RTO.
